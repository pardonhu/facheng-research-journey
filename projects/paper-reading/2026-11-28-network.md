本篇重点是**实验段落的递进**和**可比性与结论主语**。原因是“保真”容易被写成一个没有对象的总标签；作者用协议事件、业务表现、故障干预和控制回退把它落到不同可观察量。对组网写作，关键是每段回答一个明确问题，而非用一张吞吐图承担全部可信度。

### 怎样从实现过渡到实验

§5末尾先说明错误如何通过FAPI进入真实协议栈，§6开头随即把实验分成两项任务：本节检验系统本身，应用用途在§7展开。这样读者先确认工具可用，再看它能做什么。这里可借鉴的是职责顺序；具体软件和协议并非写作模板。

§6.1的段首先固定真实对照与软件版本，再分别读控制面和数据面。图5比较消息是否出现及其先后，图6比较业务量；它们回答不同问题。后面的调度配置对照又把“结果相近”推进到“改变输入后，两边是否同向变化”。

由此形成一个可用于作者稿件的检查：在写“实验与模型一致”以前，先指出比较的是哪一事件、哪一指标和哪一配置；平均结果一致后，再安排一项干预，检查系统是否仍按相同机制响应。无需把每种比较都塞进一段。

### 解释图时，先读被保持的量，再读付出的代价

§6.3.1 pp.10–11从真实云环境比较转入人为注入抢占和网络延迟。后一组实验的作用是把原因变成可控制的输入。图10(c–d)的两类量应连续解释：虚拟网络里的RTT保持相近，现实执行所需的时间伸缩增加。段末据此判断平台延迟被隔离，不能写成计算工作消失或真实运行加速。

**视觉核对。** PDF p.11图10使用蓝色RTT和红色时间伸缩轴，颜色把两种成本分开；作者选择了跨栏组图，双栏本身属于版式约束。此页还存在可复核的标注不一致：图内“Environment”标为(b)、“Processing”标为(a)，图注和正文采用相反对应。后续改稿不能只检查引用编号存在，还需把引用、子图字母、坐标内容逐项对上。本笔记按坐标和内容定位，不默默采用其中一组字母。

### 从结果走到机制，再用回退增加可信度

§7.2 p.12与图13(b–d)给出一条完整链：固定同一个UE和信道设置，先改变BLER目标；再看MCS；再看重传、拥塞窗口和有效吞吐；最后将目标调回原值，检查结果是否恢复。这里的写作价值在于，下一句解释前一句留下的疑问：MCS升高后，为什么有效吞吐反而降低？作者继续追踪可靠性和传输层响应，使读者看到中间环节。

回退提供了比单次A/B更多的证据。它可以削弱“只是随时间漂移”的解释，实验的因果范围仍对应本次固定条件下的参数干预。每轮平均值与分布、重复次数、随机变化仍应按实际记录报告。

还有一处可借鉴的审查：§6.3.3把两个云平台的差异用于讨论嵌套虚拟化。两个平台同时改变了机器与云环境，故不能将差异全部归给虚拟化。后续写作应先写“整套部署相差多少”，若要报告虚拟化的独立开销，再使用同平台开关它的对照。

### 助手原创英文改稿练习

以下差例和改稿由助手自拟，不是论文原句，也不是作者稿件。改稿中的数值依据Chronos §7.2；用途是练习连贯解释，不声称本笔记重测了这些结果。

**自拟差例：**

> Figure 13 shows the good performance of the controller. A larger BLER target increases MCS, but throughput becomes worse. This proves that our controller is accurate and reliable.

问题在于，段首没有实验任务，“good performance”没有指标，“accurate and reliable”也超出这项对照；MCS与吞吐方向相反之处没有解释。

**完整改稿：**

> We next test whether a control request produces the expected response throughout the stack. For one UE at a fixed 18 dB SINR, the xApp changes the target BLER from 0.05 to 0.20 and then restores it to 0.05, holding each setting for 150 s. The higher target raises the settled MCS from 23.9 to 25.0, while mean TCP goodput falls from 16.6 to 11.5 Mbit/s. The accompanying increase in HARQ retransmissions and decrease in the congestion window explain why the more aggressive MCS does not improve delivered traffic. After the original target is restored, MCS and goodput return to 24.0 and 16.9 Mbit/s. This reversible response supports the preservation of the tested control path in emulated time.

改法有三个实质变化。第一句把任务定为检查控制请求如何影响协议栈；第二句在结果前交代共同条件和干预顺序；中间用重传和拥塞窗口连起两种相反趋势。结尾的主语是“本次控制路径的响应”，与证据范围一致。

**对电芯组网稿的使用。** 若前文报告缩短前导提高了首次发送速度，下一段应接着问重传是否抵消这部分节省。若已有授权实验包含A–B–A配置回退，可先描述参数改变、再讲首次接收和补发，最后看整批完成时间是否恢复。缺少这些日志时，仅加入对应验证计划，不能编造中间过程或恢复结果。

### 新增原始资料

通过网页PDF解析核对了Decawave《DW3000 Family User Manual》v1.1的原始文档内容，[可访问的制造商文档存档](https://manuals.plus/m/64aa1e4d95b53cf4ecb1cdc51432f9b9c34748e261b26432895359d9d9527894.pdf)共255页。当前[Qorvo入口](https://www.qorvo.com/products/d/da008154)列出DW3110等产品并显示产品状态提示；本次可读取的具体寄存器证据来自v1.1存档，实际器件修订及驱动行为仍需实机核对。另一个Qorvo论坛附件仅有p.44双缓冲流程，不用于本节寄存器判断；本次没有取得可供本地解析的完整手册。

实际读了pp.39–41接收流程、p.95状态位、pp.100–102 RX_FINFO、pp.188–189 IP_DIAG_12：RXPACC在good PHR之后更新；IP_NACC另由CIA路径给出，条件是CIADONE，且MINDIAG必须清零。两者含义也不同，IP_NACC对SFD符号作了有效累计量处理。RXPHE与CIADONE是独立说明的状态位；手册没有在上述章节保证所有PHR失败都会产生有效CIA结果。由此应逐事件核验，而不能把“RXPACC失效”扩大为“全部前导诊断失效”。

这使首实验从“先造参考探测器”变成“先确定原芯片已经报告什么”。固定32/64/128-symbol前导，在可控干扰下按每次尝试记录RXPRD、RXSFDD、RXPHD/RXPHE、CIADONE/CIAERR、IP_NACC与可用CIR；每个字段分别标记有效性，清除旧事件并防止重新接收覆盖。先比较PHR失败且CIA完成的比例，再检查现有诊断对失败阶段和未测组合的预测力。此时没有必要新增参考发送者。

### 原创可辨识性检查

考虑一个简化复数tap。两个未知响应为 `z₊ = 0.6 + 0.8j` 和 `z₋ = 0.6 − 0.8j`。参考信号只能沿实轴调整幅度`a`，两种状态对每个`a`都给出相同的`|z+a|`。因此，任意密度的这种幅度扫描、以及只依赖该幅度的阈值事件，均无法区分它们。

现在叠加另一干扰`w = 0.8j`：前者的幅度为1.708800749，后者为0.6。在阈值1.2下，一个越界，一个没有越界。一次301点幅度枚举验证两条扫描曲线差异为0；以上恒等式本身给出对所有实数`a`的结论。复算：

```python
import numpy as np
a = np.linspace(0, 3, 301)
zp, zm, w = 0.6 + 0.8j, 0.6 - 0.8j, 0.8j
assert np.allclose(np.abs(zp + a), np.abs(zm + a))
assert abs(zp + w) >= 1.2 and abs(zm + w) < 1.2
```

[独立复算脚本](experiments/2026-11-28-network-audit/reference_phase_ambiguity.py)与[实际输出](experiments/2026-11-28-network-audit/reference_phase_ambiguity.json)一并保存。

这是助手的单tap教学反例，并非DW3110信道或饱和门槛测量。它淘汰的是“只靠同一参考相位的幅度扫描就能恢复任意相干组合”这一版本。若测到带稳定相位基准的复数CIR，或提供真正可控的多相位观测，输入信息已改变，需要另做可辨识性分析；不能用这些尚未实现的能力救回原假设。

### 当前研究判断与下一步

常规做法已经有分阶段状态位、CIA诊断、完整CIR与已知码/CFO模型。I12要解决的剩余困难必须具体到：这些观测在什么失败事件下仍缺少哪一项信息，以及增加探测后这项信息怎样变得可辨识。仅调整功率、加参考包或拟合成功率，不足以形成独立突破。

首先做上述原生诊断有效性检查；若失败时已有有效IP_NACC/CIR且强基线能预测组合，就关闭参考辅助方案。若确有信息缺失，再测参考相位和增益是否跨试次稳定，并以本文反例检验所选观测能否区分相干叠加。通过这两关之后，才讨论低成本校准和组网调度。Chronos提供的写作启发也适用于这里：先界定可观察接口及其保真对象，再报告它足以支持什么结论。

本次新增的是硬件资料核对、一个可复算反例及首实验调整；没有新增性能结果，也没有宣布可发表的突破。
