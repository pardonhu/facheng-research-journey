# FastSET 转期刊复盘与后续协作规范

整理日期：2026-10-20。

这组文档从 FastSET 转期刊的协作中提炼错误模式，供其他领域的科研、论文和 PPT 工作使用。重点不是记住某次实验用了什么参数，而是识别：为什么会把事情做错、什么时候容易重犯、用什么小动作可以提前避免。

作者在整理过程中明确纠正了方向：“应该着重对犯错的模式反省，下次在其他科研任务、不同领域里能够快速避雷。”因此，具体项目的设置和原话放在依据台账中，正文不写成 FastSET 操作手册。

这是一份经过整理的公开复盘，不是完整聊天存档，也不是当前实验的操作指令。原始数据、私人沟通和工作机信息不随文档发布。

## 两分钟先过这八个问题

1. **对象和单位是什么？** 名称相同，是否实际指同一件事？
2. **哪些决定已经确认？** 我有没有悄悄改变研究问题或重要条件？
3. **真正目标是什么？** 我是否在优化一个方便展示、却不代表目标的数字？
4. **能把结果归因给谁？** 除了研究变量，还有什么一起变了？
5. **证据支持到哪一层？** 我是否把一个局部检查通过说成整体正确？
6. **现在以哪个版本为准？** 旧要求、旧文件和旧结果是否还混在流程里？
7. **下一步能消除哪个关键障碍？** 我是在推进交付，还是做更多不必要的工作？
8. **作者最终看到什么？** 成品是否回答了问题，而且来自刚修改的内容？

这八个问题不是每次都写成八张表。一个小改动可以在脑中核对；涉及长时间计算、多人协作或正式投稿时，才把关键答案写下来。

## 文档中的证据标记

| 标记 | 含义 | 应如何使用 |
|---|---|---|
| 明确指示 | 对话中作者直接提出或确认 | 可以作为对应范围的执行要求 |
| 变更后的指示 | 作者后来修改了先前要求 | 优先执行更新版本，保留历史说明 |
| 记录核实 | 对话之外，还核对了本地修复报告、协议或修改记录 | 只证明记录中那一项，不外推为整个系统都通过 |
| 作者质疑 | 对话里提出疑问，但现有材料不足以确认原因 | 形成检查项，不能写成已证实事故 |
| 复盘建议 | 助手根据本次经历提出的方法 | 作为建议，不冒充作者原话 |
| 项目限定 | 只适用于本次稿件或某个实验 | 新项目重新确认，不机械继承数值 |

历史片段中有大量作者反馈，但并不包含每一次助手回复和所有运行日志。因此，复盘会明确区分“作者指出了这个问题”和“已核实问题根因”。公开文档不公布尚未公开的性能结果，不替论文重新裁定实验结论。有关 PPT 的迁移原则会标明来自原有组会指南或本次经验推导，不声称本次已经完成了一个不存在的 PPT 项目。

## 怎样让下一次任务真正用上

新任务开头提供这个目录，或写：

> 先按科研 journey 中的 FastSET 复盘读取相关规范。当前任务是……；主文件是……；这次特别覆盖历史规则的要求是……。先给出你理解的修改范围，然后直接执行已授权的工作。

仓库里有文件，并不等于每次协作已经读取。实际开工时，应在任务卡中写明使用了哪些文档、哪些项目限定设置不沿用。新增偏好先写入台账，再修改对应规范，避免多个文件各说各话。
