# 08 远程服务器与多 GPU 实验调度

目标是让一批实验可靠、尽快地完成，并把结果带回可分析的状态。这里的分布式主要指把独立实验分配到不同机器和 GPU；单个模型的数据并行训练是另一项设计，不自动启用。

本文件依据本次多机器协作需求整理。明确要求包括保护共享环境、主动补队列、逐卡汇报、统一正式计时、保存模型和进度。任务状态机、派发规则等是可复用的实现建议，不声称已经在本次所有服务器上完整部署。

## 1. 先掌握资源，再安排任务

只保留执行需要的信息。真实连接信息和访问凭据放在私人配置中，不进入公开经验库。

| 记录对象 | 最少记录什么 | 用途 |
|---|---|---|
| 机器 | 私有别名、可用环境、数据位置、空余磁盘、传输路径 | 判断任务能否直接启动 |
| GPU | 设备身份、当前占用、授权范围、是否停止接收新任务 | 防止抢占和误派 |
| 实验 | 唯一任务 ID、配置版本、输入来源、资源需求、预计时长 | 安排队列并防重复 |
| 执行尝试 | 所在机器、进程身份、开始时间、日志、输出目录 | 排查失败并恢复 |

可用 GPU 需要同时满足：当前健康、当前空闲或符合共享约定、用户有权使用。不能只看显存空闲，也不能因过去报错就永久排除。派发前刷新状态，避免其他人已开始运行而调度器仍按旧快照分配。

设备要能追溯到物理卡。框架中的设备编号可能与宿主编号不同，记录实际映射；不要只留下一个无法定位的“GPU 0”。

## 2. 环境和数据先准备好，形成随时可跑的队列

有效的流水线是：

> 配置确认 → 数据和环境就绪 → 分配 GPU → 执行 → 验收输出 → 回传 → 统计画图。

把“待准备”和“可执行”分开。GPU 空出来以后才开始找数据、修路径、装环境，会让并行失去意义。

可复用的做法：

- 同一环境先在一张卡上跑有针对性的小验证，通过后供同批任务复用；环境或输入发生相关变化时再核查。
- 原始数据尽量一次传输、多任务只读共享。配置和结果按任务隔离，不为每个候选复制完整数据集和整套代码。
- 两台远程机器之间有合适的直接传输路径时，可避免反复经本机中转；先确认实际可达和磁盘容量。
- 空间预算同时考虑源文件、压缩包、解压副本、checkpoint 和临时结果。避免“包本身放得下，解压却放不下”。
- 大文件打包、预处理与回传也有限速和并发需求。它们不能把负责训练或计时的机器拖慢。

环境优先使用自己的隔离环境；系统驱动、共享库和其他人的进程不属于普通实验修复范围。

## 3. 任务拆到可以独立完成、可以独立恢复

通常按候选模型、场景、seed 或一次完整训练拆分。每项都有自己的配置和输出目录，多个任务复用同一份公共实现。

一个任务记录可采用以下字段，按项目裁剪：

```text
任务 ID / 配置版本 / 输入与 checkpoint 来源
依赖 / 优先级 / 显存与 CPU 需求 / 预计时长
当前状态 / 负责人 / 所在机器与 GPU
执行尝试 ID / 日志 / 输出 / 验收标准
```

不要为提高并发而随意拆开一个有状态的训练过程。接续训练需要保存相应模型、optimizer、RNG 和数据进度；若协议只要求重新初始化再跑，应明确记录重跑，不冒充连续恢复。

## 4. 用简单规则实现高效派发

优先级先由研究目标决定，再考虑机器利用率：

1. 优先执行会解锁后续一批工作的任务，例如公共数据准备、源模型训练、关键兼容性验证。
2. 在同一优先级里，尽早启动长任务，避免短任务全完成后只剩一个长任务拖尾。
3. 把显存、数据位置、环境需求相匹配的任务派到对应机器，减少迁移与等待。
4. 用短任务填补已知的可用时间窗口；正式计时需要独占时，不在旁边安排干扰任务。
5. 每次完成、失败或资源授权变化后重新排队，不把最初计划当成永久安排。

估时根据已经完成的同类任务更新。不同设备不能直接套同一个吞吐；首次编译和稳定运行阶段也要区分。

“尽量同时完成”不等于把任务数平均分。更合适的是平衡预计剩余时长和依赖。GPU 空闲时，先检查可执行队列、可提前准备的依赖和可迁移任务；没有合适的授权任务时，说明原因，不临时创造无关实验。

## 5. 防重复的关键是任务认领，不只是启动命令

建议使用一份权威任务表，并让认领操作互斥。可以采用适合项目规模的单一调度者或支持原子更新的存储，不要求一开始搭建复杂平台。

一种简单状态划分是：

```text
待准备 → 可执行 → 已认领 → 运行中 → 待验收 → 已完成
                         ↘ 失败 / 暂停 / 已取消
```

关键规则：

- 认领成功后才能启动；任务只有一个当前负责人。
- 重试创建新的尝试记录，保留旧日志和失败输出。
- 断线或心跳超时不代表进程已停止。重新派发前先核对远程进程与输出，防止两个副本同时训练。
- 进程退出成功之后，还要检查预期结果、配置身份和完整性，才能标记“已完成”。
- 本机锁只能协调遵守该锁的进程，不能据此认为其他同学不会使用那张卡。

跨会话接管时，先移交任务归属，再启动远程执行；不要让原会话继续派发同一批后续任务。

## 6. 让远程执行不依赖聊天窗口

需要无人值守时，实际部署适合环境的作业管理或进程托管机制，并确认断开控制连接后仍能工作。仅把命令发到远端，不等于已经具备自动恢复能力。

至少能够回答：

- 进程是否还活着，最近是否有有效进度？
- 日志和 checkpoint 在哪里？
- 失败后谁负责处理，允许重试几次？
- 用户要求“当前任务跑完就停止派发”时，在哪里改变状态？
- 本机关机后，哪些远程任务继续，回来如何接管？

自动恢复只处理已理解、不会改变科学协议的故障。例如可恢复的传输中断可以续传；持续出现数值异常、数据不完整或内存不足时，应停止盲目重试，先诊断。不能自动减小 batch size 或更换模型后，把结果继续当成原任务。

## 7. 用进度、资源和产出联合监控

| 观察 | 可以说明什么 | 下一步 |
|---|---|---|
| 显存占用低 | 可能处于输入准备、等待或较小计算阶段 | 看实际进程、GPU 计算活动和日志进度 |
| 进程存在但长期无新进度 | 可能在编译、读取、通信或卡住 | 对照阶段和正常耗时，定位等待点 |
| 多任务一起变慢 | 可能争用 CPU、磁盘、网络或设备 | 看共享瓶颈，调整准备与传输并发 |
| 温度持续偏高 | 需要遵守机器所有者的运行约定 | 通知、减少自己的并发或暂停自己的任务 |
| 输出已有结果但队列未完成 | 可能验收或状态更新失败 | 核对输出后修复状态，避免重跑 |

温度与运行限制按设备和所有者约定设置，不把某次对话中的温度值推广为所有硬件的安全标准。

## 8. 远程训练与统一计时可以分工

独立训练、验证可以分散到多张卡，提高吞吐。正式比较运行时间时，把候选带回约定的基准环境，按同一计时协议测量。

若采用“先记录性能轨迹，再去掉评估重放计时”的方法，要保持相同起点、输入顺序、更新次数和相关状态，并保留两次执行的对应关系。重放路径的可比性需要依据，不能仅把两个文件按 iteration 拼起来。

远程测得的时间保留为运行记录，不混入统一设备上的正式加速比。机器快慢和方法快慢是两个不同问题。

## 9. 完成一个任务，就回收一个可用结果

结果回传不必等整批结束。按任务回收最小可用包：配置、环境版本、指标表、日志、必要 checkpoint 和状态说明。

已有 checkpoint 以后可能用于新目标域、不同评价规则和后处理分析，值得有计划地保存；是否保留全部中间状态要看空间与潜在用途。不要无限存，也不要为了腾空间删掉唯一能支撑论文结论的状态。

结果验收后进入汇总队列。重画图、改变已有轨迹的统计方式，通常优先利用已有结果；新规则需要此前未保存的状态时，再明确需要补跑哪部分。

## 10. 汇报到每张卡，并解释下一步

| 机器/GPU | 当前任务与进度 | 预计剩余 | 下一任务 | 状态或空闲原因 |
|---|---|---|---|---|
| 私有别名/设备身份 | 任务 ID、阶段、实际完成量 | 有依据的估计 | 已就绪任务或待依赖任务 | 运行、准备、计时保留、停止派发等 |

表后只补三个总量：已经完成多少、还有多少可执行、多少被依赖卡住。说明下一步如何缩短整体完成时间，比只汇报“几张卡在跑”更有帮助。

## 11. 下次可以直接复用什么

沉淀下来的是资源登记字段、任务认领规则、环境与数据准备顺序、结果包结构、恢复流程和逐卡汇报模板。真实主机连接、凭据、权限及当前队列留在私人配置中。

先用少量任务跑通“准备—派发—执行—验收—回传”，再扩大并发。这样增加机器时，主要增加的是容量，而不是重新组织一次实验。
