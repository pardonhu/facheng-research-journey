# 05 协作与交接：主动不等于失控

本次多会话、多机器协作暴露的问题，可以推广到任何多人科研项目：任务不缺，缺的是清楚的归属、依赖和完成状态。

## 1. 只维护一份当前有效状态

最低限度记录：

```text
当前目标：
主文件 / 主数据 / 主配置：
我负责：
其他人负责：
已完成：
正在执行：
下一项：
已取消或关闭：
```

不要另写一份详细计划，却让真实队列继续使用旧设置。状态文件应反映实际执行，而不是愿望。

## 2. 拆任务按依赖和文件边界

适合并行的是独立输入准备、互不覆盖的实验、分开的图表和证据核对。不适合同时写的是同一个主稿、同一套全局风格、同一个结果表。

交给另一会话时，明确输入、输出、禁止改动的范围和接管时点。不能只说“你跑 RT，我跑其他”，然后双方都继续派发共同的后续任务。

作者说某项任务由 side 会话处理时，主会话只对接结果，不重复训练或抢着改它的图。

## 3. 执行中的暂停与恢复

作者要求停机或停止实验时：

- 停止派发新任务；
- 保存进度、当前运行身份、checkpoint 或中间结果；
- 区分本地任务与仍在远端运行的任务；
- 写清恢复入口与已完成任务，避免重启后重复计算；
- 不擅自终止他人的进程。

恢复时先核对现状，不直接重放旧命令列表。新日期、可用卡和用户授权可能已经变化。

## 4. 主动处理阻塞，但不要靠扩大权限解决一切

数据没准备好，就优先准备；共享 GPU 不可用，就把适合的任务调到已授权的其他资源。环境问题优先在自己的环境中隔离解决。

不能因为作者催进度，就修改共享系统驱动、停止其他人的任务或跳过决定正确性的关键条件。

对于反复失败的任务，保留失败证据、限制重试次数、报告当前最可能的原因。不要无限自动重试，使“无人值守”变成无人知道在浪费资源。

## 5. 不作虚假的持续监控承诺

“我会一直盯着”只有在实际存在持续运行的进程、调度器或其他可靠机制时才有意义。

说明：

- 哪个机制继续工作；
- 日志在哪里；
- 如何发现失败；
- 自动恢复范围和停止条件；
- 什么情况需要人工介入。

如果只有当前聊天执行，就不能把一段结束语包装成已经部署的自动监控。

## 6. 汇报的最小内容

先回答作者当前问题，再给任务全貌：

| 部分 | 应包含 |
|---|---|
| 新进展 | 真正完成了什么，结果说明什么 |
| 当前执行 | 哪项任务、什么阶段、在哪个资源上 |
| 队列 | 接下来跑什么，依赖是否准备好 |
| 阻塞 | 原因、影响、已采取的动作 |
| 决策 | 是否需要作者决定；不需要就继续执行 |

汇报不要只说文件数量，也不要隐藏没有开始的任务。估时应依据当前吞吐、剩余工作量和争用情况，明确估算，不用显存百分比推断剩余时长。

## 7. 关闭问题，保留事实

作者已确认另一会话完成复核或明确要求不再处理时，应记录关闭依据并继续工作。原始失败日志保留，不修改为成功记录。

此后只有出现新的、直接相关的信息，且影响当前任务，才值得再次提出。不能每次开工都把旧疑虑当作新问题。

本次案例中的已关闭事项，在本复盘中只用于总结模式，不作为重新执行的任务清单。

## 8. 公开仓库与私人工作区分开

公开可复用的是：方法、偏好、流程、例子和经过整理的经验。

不应随复盘公开的是：登录信息、原始聊天、机器地址和账户、私人作者沟通、未经授权公开的结果表、模型或数据。

具体任务记录可留在本地。提交前按实际文件检查，不靠一句“已经脱敏”替代检查。

## 9. 交付要减少下一位协作者的启动成本

一份有效交接应让对方不必重新问：

- 现在到底在做哪个问题？
- 哪个版本是真的？
- 哪些结果可以复用？
- 哪些设置不能改？
- 谁还在改同一个文件？
- 下一步怎样做才不会重复或冲突？

作者最看重的是减少这些重复沟通，而不是交接文档越长越好。
