# 02 科研任务执行协议

适用于实验、数据分析、仿真、模型训练和系统测量。它是一套轻量工作顺序，不预设领域、工具或具体参数。

## 1. 先把需求改写成一个判断

不要从“运行哪些脚本”开始，而从“完成后要判断什么”开始。

例如：

- 这次实验要判断新方法是否在相同可靠性要求下减少成本。
- 这次消融要判断哪个模块在什么条件下有用。
- 这次复现要判断两套实现是否在约定输入上计算一致。
- 这次分析要判断差异来自处理方法，还是来自样本构成。

一句话说不清最终判断时，先读已有方案和结果；不要立即扩大实验矩阵。

## 2. 建立最小任务约定

只记录影响执行的关键内容：

| 必填问题 | 为什么不能省略 |
|---|---|
| 研究对象与输入是什么 | 避免名称相同但对象不同 |
| 比较条件和允许变化的因素是什么 | 避免混淆变量 |
| 指标和单位是什么 | 避免优化错目标 |
| 预算和停止条件是什么 | 避免无界运行或提前截断 |
| 数据及模型来自哪里 | 避免起点已经包含目标信息 |
| 什么证据算完成 | 避免只交日志不交结果 |

如果这些已经在当前协议中清楚写明，引用一次即可，不要复制成多份容易过期的表。

## 3. 优先做能区分问题的小验证

小验证不是把正式实验随便缩小。它必须回答一个具体风险：

- 读入的对象是不是预期对象？
- 数据预处理是否改变了单位、形状或物理含义？
- 优化步骤是否真的更新了指定部分？
- 计数是否覆盖全部样本？
- 一次试运行是否遵守预算与停止条件？

通过以后再扩大。发现问题时定位到最小环节，避免同时重装环境、修改实现和更换输入，使诊断失去依据。

如果用户已经明确要求跳过重复核验，要利用已有可信证据；只有直接影响当前执行的新问题才值得再次检查。

## 4. 区分四种“相同”

| 声称 | 实际含义 |
|---|---|
| 相同结构 | 计算图、模块和参数形状一致 |
| 相同起点 | 数据、模型状态、必要 optimizer/RNG 状态符合约定 |
| 相同计算 | 在指定环境与输入下，输出或更新满足数值判据 |
| 相同结论 | 在研究条件和不确定性范围内支持同一判断 |

前一种不会自动推出后一种。反过来，小浮点差异也不能未经分析就被当成科学结论不同。

使用“复核通过”时说清是哪一层，不把一次成功包装成无限范围的保证。

## 5. 评价流程必须符合使用场景

不同问题需要不同预算：

- 衡量达到目标的成本：记录首次达标点。
- 研究完整收敛行为：运行固定预算并记录轨迹。
- 搜索候选方案：明确允许选择的范围、参考对象和评分方法。
- 评价未知环境：固定事先选定的方案，再执行约定测试。

选择哪一种是研究设计。不能为了图形更好看临时切换，也不能把一种流程下的时间与另一种流程下的性能拼成一个方案。

**迁移原则：** 需要一致的是评价含义，不一定是所有方法机械地运行相同次数。例如每一步成本不同，单看次数未必公平；若每次处理的数据量不同，固定次数也不等于固定样本量。

## 6. 时间和成本都要有边界

计时前写清三件事：

1. 测量对象：计算核、完整处理流程、冷启动，还是常驻服务中的一次适应。
2. 包含和排除的操作：读取、处理、通信、计算、验证、存盘等。
3. 运行条件：设备、缓存、并发、预热和同步。

本次案例最终采用“常驻、预热后的输入处理加训练，排除评估”。这是具体项目决定，不是通用答案。

旧记录缺少某部分成本时，先看是否能利用已有实测。需要补测，就只补缺失部分，并明确它是连续实测还是组合统计。不能把估算说成测量，也不能重复计入已包含的操作。

## 7. 给意外结果一条短诊断路径

结果比预期好或差时，依次检查：

1. **身份**：数据、权重、对象、单位有没有拿错？
2. **协议**：预算、停止条件、评价集合、运行环境有没有变？
3. **实现**：必要模块是否参与，冻结、损失和预处理是否正确？
4. **解释**：排除直接错误后，这是否是一个真实的新现象？
5. **最小验证**：哪一个便宜的对照最能区分剩余解释？

不要从第一步直接跳到“方法失效”“数据泄漏”“随机性导致”或“结果太好所以应该重做全部实验”。

作者的期望可以决定关注什么问题，不能替代观察结果。原来的最佳方案被新流程超越，本身不是失败；应解释哪些评价条件改变、揭示了什么以前没有看见的优势。

## 8. 根据关键路径使用资源

资源调度以缩短已授权任务的完成时间为目标：

- 先准备即将运行的任务所需数据和环境；
- 独立训练或计算可并行，可比性要求高的正式测量保持约定条件；
- 当前故障要按现状判断，历史故障记录不是永久禁用证据；
- 不能改共享机器的系统环境来换取个人便利；
- 大文件打包、传输、CPU 预处理也会与训练争用资源；
- 没有合适的已授权任务时，空闲比启动无关任务更好。

不能承诺“随时都有 GPU 跑”而忽略共享权限、独占计时或任务依赖。

## 9. 保存能支持结论的最小结果包

通常包括：

- 当前协议与变更记录；
- 数据和模型来源；
- 原始可计算的结果表；
- 有单位的统计值与样本数量；
- 运行日志和失败状态；
- 可复用的图代码、最终图与结论说明。

不同 run 分开保存，共享实现和原始只读输入。结果包应让下一位协作者回答“这个结论从哪里来”，而不是要求他重跑整个项目。

## 10. 给任务一个明确的终点

达到约定的验收条件后交付。不要因为还有空闲资源，就无限加入 seed、环境或参数。

确有新发现值得扩展时，先说明它能增加什么认识、预计成本是多少；与当前任务的完成状态分开。作者取消某项实验后，保留已有数据，不再让它隐式留在队列里。
